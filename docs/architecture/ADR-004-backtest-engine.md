# ADR-004: 回测引擎设计

| 字段 | 值 |
|------|------|
| **ID** | ADR-004 |
| **状态** | 已批准 |
| **日期** | 2026-05-12 |
| **决策者** | Tech Lead |
| **影响范围** | 回测模块、数据模型、计算性能、结果可靠性 |

## 背景

PRD 要求回测引擎必须模拟交易成本和滑点，回测夏普比率误差 < 5%。这是量化交易系统最关键的差异化功能——不可靠的回测比没有回测更危险。

核心要求：
- 支持任意时间段的历史回测
- 模拟交易成本（手续费率可配置）
- 模拟滑点（基于流动性和订单量）
- 计算 7 个核心指标（总收益率、年化收益、最大回撤、夏普比率、胜率、交易次数、盈亏比）
- 显示资金曲线并标注回撤区间
- 1 年 1h 数据回测时间 < 30s

## 架构方案

### 选项 A: 全内存向量化计算 ✅ 选定

**设计：**
- 一次性加载历史 K 线到内存（Vec 结构）
- 遍历每根 K 线，逐 tick 执行策略逻辑
- 记录每笔交易信号，模拟撮合
- 批量计算统计指标

```
┌──────────────┐    ┌─────────────────┐    ┌──────────────┐
│  输入参数     │───→│  引擎核心         │───→│  结果写入 DB  │
│  - 策略ID     │    │  - 加载K线到内存  │    │  - metrics   │
│  - 开始/结束   │    │  - 逐根K线模拟   │    │  - trades    │
│  - 初始资金    │    │  - 手续费计算    │    │  - equity    │
│  - 手续费/滑点  │    │  - 滑点模拟     │    │  - curve     │
└──────────────┘    │  - 性能指标计算   │    └──────────────┘
                    └─────────────────┘
```

**优势：**
- 性能高：无 IO 等待，纯 CPU 计算
- 逻辑简单：线性执行，易于调试
- Rust Vec 遍历极快，1 年 1h 数据仅 8760 根 K 线
- 适合基于 K 线的策略（非逐笔 level-2）

**劣势：**
- 内存占用随数据量线性增长（10 年 1h ≈ 87K bars，不足 10MB）
- 不可用于逐笔回测（tick-level simulation）
- 不支持 order book 级别的撮合

### 选项 B: 事件驱动逐笔回测

**优势：** 更高精度，支持 order book 模拟
**劣势：** 复杂度高、计算慢、数据需求大（需全部 level-2 数据）

### 选项 C: 调用外部回测库 (例如 backtrader)

**优势：** 功能完整，社区成熟
**劣势：** Python 依赖，性能差，调试困难，与 Rust 集成复杂

## 详细设计

### 回测流程

```
1. 参数校验（时间、金额、费率）
2. 从 PostgreSQL 加载历史 K 线数据（查询 kline_data 表）
   → 按 symbol + interval + timestamp 排序
3. 初始化回测状态：
   - 账户：初始资金、当前权益、冻结资金
   - 持仓：空
   - 交易记录：空列表
4. 逐根 K 线执行策略逻辑：
   a. 更新 bar 数据到策略上下文
   b. 策略计算交易信号（MA cross, RSI, etc.）
   c. 如有信号，检查是否已持仓 → 平仓/开仓
   d. 成交计算：
      - 限价单：比较 bar 高低价，确定是否成交
      - 市价单：按 close 价成交
      - 手续费 = 成交金额 × 费率
      - 滑点 = 成交价 × 滑点率（正/负各半随机）
   e. 更新持仓、资金、保证金
   f. 记录 trades 到结果列表
5. 计算性能指标
6. 返回值：metrics JSON + trades list + equity curve
```

### 滑点模型

```
slippage_price = execution_price × (1 ± slippage_rate × random_sign())
  买入：slippage = +slippage_rate（支付溢价）
  卖出：slippage = -slippage_rate（接受折价）
  默认滑动率：0.05%（可配置）
```

### 线程模型

- 回测运行在独立的 tokio blocking task 中
- 主线程不阻塞，前端通过 WebSocket 推送进度
- 进度 = 当前 bar 索引 / 总 bar 数 × 100%

## 决策

采用 **全内存向量化计算**，运行在 tokio blocking task 中。

| 特性 | 设计 |
|------|------|
| 数据加载 | 1 次查询加载全量 K 线到 Vec |
| 执行模式 | 逐 bar 串行，不影响其它回测 |
| 并发 | 每个回测独立 task，最多 5 个并行 |
| 进度 | 每 10% 推送 WS 进度事件 |
| 计算指标 | 一阶段：Vectorized returns (纯计算)；二阶段：逐笔 if-else (纯分支) |
| 结果存储 | metrics JSON 存 backtest_results 表；trades 数组另存 |

## 预期后果

**正面：**
- 1 年 1h 回测 < 5s（远超 PRD 30s 要求）
- 夏普比率误差 < 5%（因为策略逻辑 = 回测逻辑）
- Rust 性能保障，无 GC 停顿

**负面：**
- 不支持逐笔 level-2 回测（可通过二期扩展）
- 大时间段（5 年 1m）→ 约 1.3M bars → 内存和计算时间增加
