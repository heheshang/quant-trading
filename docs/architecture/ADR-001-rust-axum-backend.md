## 背景

量化交易系统对性能、并发和可靠性有极高要求。技术选型需要同时满足：
- **低延迟**：行情处理和交易信号计算要求微秒级响应
- **高并发**：支持 ≥ 1000 同时在线用户 + ≥ 20 个策略实例并发运行
- **类型安全**：避免运行时类型错误导致的交易事故
- **内存安全**：禁止空指针、野指针、缓冲区溢出等内存安全问题

## 技术选项

### 选项 A: Rust + Axum (选定)

**优势：**
- 零成本抽象，性能接近 C/C++，单实例可处理 10 万+ 并发连接
- 所有权系统保证内存安全，编译期消除整类 bug
- Axum 基于 tokio + tower，生态成熟，中间件栈简洁
- SeaORM 提供类型安全的异步 ORM，编译期验证 SQL
- 1 二进制部署，无运行时依赖

**劣势：**
- 学习曲线陡峭，招聘成本高
- 编译时间长，迭代速度慢
- Rust crate 生态虽好但不如 Node/Python 丰富

### 选项 B: Node.js + Express/Fastify

**优势：** 开发效率高，NPM 生态丰富，异步 IO 模型成熟
**劣势：** 单线程事件循环在高 CPU 场景下堵塞，类型安全不足（即使 TS 也有 `any` 漏洞），GC 停顿不可控

### 选项 C: Python + FastAPI

**优势：** 开发者易找，数据分析(Pandas/Numpy)生态强，回测原型快
**劣势：** GIL 限制多核利用，高并发场景下表现差，ASGI 异步栈复杂度高，运行时类型检查不如编译期可靠

| 属性 | Rust | Node.js | Python |

| 性能 | ★★★★★ | ★★★ | ★★ |

| 生态成熟度 | ★★★ | ★★★★★ | ★★★★★ |

## 决策

采用 **Rust 2024 edition + Axum 框架** 作为后端技术栈。配套使用：
- **SeaORM** 或 **SQLx** 编译期检查 SQL
- **tokio** 异步运行时 + **tokio-tungstenite** WebSocket
- **jsonwebtoken** crate 实现 JWT 鉴权
- **tracing** crate 实现结构化日志
- **tokio-cron-scheduler** 实现定时任务

## 预期后果

**正面：**
- 高性能、低延迟、高可靠的后端基础
- 编译期消除安全漏洞，降低运行期事故风险
- 单二进制部署，运维简洁
- 策略引擎可安全并行运行多个实例

**负面：**
- 需要为 Rust 开发者支付更高薪资或投入培训成本
- 原型迭代速度低于 Python/Node
- 策略脚本执行需要额外沙箱设计（Rust 不能直接运行 Python 脚本）
