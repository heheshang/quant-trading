# 量化交易系统 — 风险点与缓解措施

> 版本: v1.0 | 评估者: Tech Lead

---

## 风险总览

| 严重度 | 数量 | 说明 |
|--------|------|------|
| 🔴 Critical | 3 | 必须解决才能上线 |
| 🟠 High | 5 | 强烈建议解决 |
| 🟡 Medium | 4 | 推荐在后续迭代解决 |
| 🟢 Low | 3 | 可接受当前设计 |

## 🔴 CRITICAL 风险

### CR-01: 策略引擎无法直接运行 Python 策略代码

| 字段 | 值 |
|------|------|
| **模块** | 策略管理 |
| **描述** | PRD 描述用户 "编辑策略代码（Python/Pine Script 语法高亮）"，但后端是 Rust，不能直接运行 Python 或 Pine Script 代码。这是一个**架构级冲突**，会影响核心用户体验。 |
| **影响** | 高风险。MVP 功能需重新设计。用户无法编写自由策略，只能使用模板。 |
| **缓解** | **分阶段处理：** MVP 阶段使用 **内置策略模板 + 参数配置**（覆盖 80% 常见策略）。第二阶段通过 **WASM 沙箱** 支持自定义策略（用户写 Rust DSL 编译为 WASM）。第三阶段可选 **PyO3 + Linux namespace** 支持 Python 策略。详见 ADR-003。 |
| **负责人** | Tech Lead |
| **状态** | ⏳ 已规划，待实现 |

### CR-02: 撮合引擎缺失

| 字段 | 值 |
|------|------|
| **模块** | 交易执行 / 回测 |
| **描述** | PRD 要求模拟模式交易（不实际发往交易所）和回测撮合。但系统目前没有 **本地撮合引擎** 来模拟订单簿匹配。模拟模式下委托无法自动成交。回测中也需要模拟撮合。 |
| **影响** | 高风险。模拟交易完全失效，回测无法产生交易信号。 |
| **缓解** | **设计独立的 `matching_engine` 模块：** 1) 模拟模式使用本地 order book + 最新价（来自行情）进行撮合 2) 回测模式使用 K 线 OHLC 进行撮合（开盘价成交/高低价突破判断）3) 实盘模式直接透传至交易所 API。该模块需在交易模块编码前完成。 |
| **负责人** | Backend Dev |
| **状态** | ⏳ 已规划，待实现 |

### CR-03: 回测数据精度与滑点模型验证不足

| 字段 | 值 |
|------|------|
| **模块** | 回测引擎 |
| **描述** | PRD 要求 "回测夏普比率误差 < 5%"，但 K 线级回测天然忽略盘口内价格波动，导致精度不足。滑点模型是随机数模拟，但实际滑点高度依赖流动性。 |
| **影响** | 高风险。回测结果可能过于乐观，导致用户根据虚假回测结果进行实盘交易产生亏损。 |
| **缓解** | 1) 技术层面：基于 K 线 OHLC 的高/低价做成交判断，而非简单用收盘价 2) 滑点模型增加基于成交量和订单簿深度动态计算（非固定值）3) **UI/UX 层面**：在回测报告上明确标注 "回测表现不代表实盘结果" 的免责声明 4) 提供一个实盘模拟差价对比（在策略同时运行模拟和实盘一段时间后对比 |
| **负责人** | Tech Lead + PM |
| **状态** | ⏳ UI 免责声明可立即执行，算法优化需二期 |

## 🟠 HIGH 风险

### HR-01: WebSocket 连接管理瓶颈

| 字段 | 值 |
|------|------|
| **模块** | 行情模块 |
| **描述** | 1000 同时在线 + 多频道订阅 → 每个客户端的连接状态、频道订阅列表、心跳需要在内存中维护。单机 1000 连接对 tokio 无压力，但多实例部署时，用户可能连接不同实例，行情数据需要跨实例广播。 |
| **影响** | 多实例部署时连接管理复杂度上升。 |
| **缓解** | 1) 使用 **Redis Pub/Sub** 做跨实例广播 2) WebSocket 无状态化——通过 Redis 记录用户频道订阅 3) 单实例初期可承载 2000+ 连接，满足 MVP 需求 4) 负载均衡使用 **ip_hash** 或粘性会话保持亲和性 |
| **负责人** | Backend Dev |
| **状态** | ⏳ 已设计，需实现 Redis Pub/Sub |

### HR-02: 行情数据延迟超 500ms

| 字段 | 值 |
|------|------|
| **模块** | 行情模块、市场数据管道 |
| **描述** | 数据管道：Exchange → Collector → Redis → WS Hub → Client，全程至少 3 跳，每跳增加延迟。交易所 API 限流、网络波动、Redis 拥堵均可能导致端到端延迟超过 500ms。 |
| **影响** | 直接违反 PRD 性能指标。 |
| **缓解** | 1) Collector 和 WS Hub 之间使用 Redis Pub/Sub（延迟 < 1ms）而非 stream 或 list 2) Collector 到 Exchange 使用 WebSocket（而非 REST polling） 3) 连接同一数据中心（同机房部署减少网络延迟）4) 监控并告警端到端延迟 |
| **负责人** | Backend Dev |
| **状态** | ⏳ 已设计，待实现后压测验证 |

### HR-03: 多策略并发执行资源竞争

| 字段 | 值 |
|------|------|
| **模块** | 策略引擎 |
| **描述** | ≥ 20 个策略实例并发运行，每个策略接收行情数据、计算信号、生成委托。策略可能互相抢占 CPU、同持仓冲突（同一 symbol 的多个策略同时开仓/平仓）。 |
| **影响** | 策略间干扰，不可预期行为。 |
| **缓解** | 1) 每个策略运行在独立的 **tokio task** 中，使用独立 channel 接收行情 2) 设置每个策略的 CPU 时间配额（tokio::time::timeout）3) 同 symbol 的多个策略通过 Risk Manager 串行化（交易信号汇聚到 Risk Manager 后统一判断）4) 设置全局最大并发策略数 |
| **负责人** | Backend Dev |
| **状态** | ⏳ 已设计，需实现策略隔离 |

### HR-04: API 安全性 —— JWT Token 黑名单性能

| 字段 | 值 |
|------|------|
| **模块** | 用户系统 |
| **描述** | JWT logout 需要将 access_token 加入黑名单。如果不做 jti 黑名单，登出后 token 仍然有效。但黑名单需要每次请求都查 Redis，增加了延迟。9 分钟内（剩余 token 有效期）检查全量黑名单可能成为瓶颈。 |
| **影响** | 安全漏洞或性能瓶颈。 |
| **缓解** | 1) 使用 **Redis** 存储黑名单，key = `token:blacklist:{jti}`，TTL = access_token 剩余有效期（自动过期无需清理） 2) access_token 有效期仅 15 分钟，黑名单存储量很小 3) Redis GET 操作 O(1)，1ms 内完成，不影响 P99 延迟目标 4) 可选的二级优化：本地 LRU cache 缓存最近 1000 个黑名单 jti |
| **负责人** | Backend Dev |
| **状态** | ⏳ 已设计，需实现 |

### HR-05: 用户策略的无限循环/内存泄漏风险

| 字段 | 值 |
|------|------|
| **模块** | 策略引擎 |
| **描述** | 用户编写的策略代码（即使通过 WASM 沙箱）如果包含无限循环或内存泄漏，将会耗尽线程资源和内存。 |
| **影响** | 系统崩溃或性能下降。 |
| **缓解** | 1) WASM 沙箱天然限制：wasmtime 可设置内存上限（64MB）和指令数上限 2) tokio task 包装器：每个策略 task 设置 `tokio::time::timeout(1s, strategy_tick)` 3) watchdog 线程：每 tick 检查策略状态，连续 N 次超时则自动停止策略 4) Python 子进程使用 cgroup 限制内存 |
| **负责人** | Backend Dev |
| **状态** | ⏳ 依赖 ADR-003 实现 |

## 🟡 MEDIUM 风险

### MR-01: K 线海量数据存储性能

| 字段 | 值 |
|------|------|
| **模块** | 行情模块、数据库 |
| **描述** | 1 个交易对 1m K 线每天约 1440 条数据，覆盖 100 个交易对，1 年约 5256 万行。单表存储可能导致查询性能下降。 |
| **缓解** | 1) 使用 **分区表**（按月或按 symbol） 2) 低精度数据定期清理（1m 保留 30 天） 3) 查看 CHERR-1 关于 TimescaleDB 的替代建议 4) 历史回测查询可通过缓存（对同一时间段重复查询不重复扫表） |
| **状态** | ⏳ 分区方案已设计，可 MVP 后实施 |

### MR-02: 回测结果数据膨胀

| 字段 | 值 |
|------|------|
| **模块** | 回测模块 |
| **描述** | 每个回测的 equity_curve 和 trades 数组大小可能很大（1 年 1h 数据约 8760 个 equity 点，每个 trade 数十到数百条记录）。JSONB 存储在大数据量下性能不佳。 |
| **缓解** | 1) equity_curve 采样存储（仅存关键节点，如每日收盘权益） 2) 逐笔 trades 使用独立表（而非 JSONB 数组） 3) 回测结果压缩存储（zlib 压缩 equity_curve 数组） 4) 超过 500 笔 trade 时前端自动分页 |
| **状态** | ⏳ 可优化 |

### MR-03: 模拟资金与实盘资金混淆

| 字段 | 值 |
|------|------|
| **模块** | 交易模块 |
| **描述** | 同一用户同时有模拟和实盘交易，positions 表的 mode 字段区分。但如果用户误操作或 UI 显示混淆，可能导致模拟操作影响到实盘账户，或反向亏损。 |
| **缓解** | 1) UI层面：模拟模式使用明显不同的主题色（橙色/紫色) vs 实盘（红色/绿色），并始终显示 "📊 模拟" 或 "💰 实盘" 角标 2) API 层面：模拟和实盘使用不同的路由前缀或在请求体中强制传 mode 参数 3) 风控层面：模拟模式也模拟资金限制，培养用户习惯 |
| **状态** | ⏳ UI 设计规范需纳入前端开发 |

### MR-04: 前端内存泄漏（长时间打开行情页面）

| 字段 | 值 |
|------|------|
| **模块** | 前端 |
| **描述** | 用户长时间打开 K 线页面，WebSocket 持续推送数据。ECharts 大量数据点可能导致浏览器内存占用持续增长。 |
| **缓解** | 1) K 线数据限制显示 500 根，更早的数据从缓存中剔除 2) ECharts 启用 `sampling` 选项 3) Canvas 渲染（非 SVG 模式） 4) 切换页面时断开 WS 连接 5) 内存使用监控告警 |
| **状态** | ⏳ 前端编码时处理 |

## 🟢 LOW 风险

### LR-01: 浏览器端 Token 存储安全

| 字段 | 值 |
|------|------|
| **描述** | access_token 和 refresh_token 存储在 localStorage 中，易受 XSS 攻击窃取。 |
| **缓解** | 1) 前端严格控制 XSS 防护（Vue 默认转义输出、CSP 头） 2) 考虑使用 **httpOnly Cookie** 存储 refresh_token（需后端设置 Cookie 端点） 3) refresh_token 一旦被窃取，攻击者只能获取 15 分钟的访问权限 |
| **状态** | ✅ 当前设计可接受，可后续优化 |

### LR-02: 数据库迁移与版本管理

| 字段 | 值 |
|------|------|
| **描述** | 使用 SeaORM Migration，但随着 CR 迭代，schema 变更可能引起兼容性问题。 |
| **缓解** | 1) 使用 **SeaORM Migration** 管理版本 2) 每个 PR 必须包含正向 + 回滚 migration 3) CI/CD 中自动执行 migration 测试 4) 生产数据库变更需审查 |
| **状态** | ✅ 流程已确定 |

### LR-03: Docker 镜像大小

| 字段 | 值 |
|------|------|
| **描述** | Rust 编译产物虽小，但多阶段构建如果配置不当，rust:latest 镜像可能超过 1GB。 |

| **状态** | ✅ 已在 TECH_CHARTER 中规范 |

## 架构建议（非风险，但推荐）

### CHERR-1: 考虑使用 TimescaleDB 替代普通 PostgreSQL 分区

针对 K 线时间序列数据（kline_data 表），**TimescaleDB**（PostgreSQL 扩展）提供了自动分区、连续聚合、保留策略等功能，比手动分区表更省心。

推荐在当前 PostgreSQL 实例上安装 TimescaleDB 扩展（开源免费），将 kline_data 表转为 hypertable。

### CHERR-2: 回测与实盘策略代码复用

确保回测引擎和实盘策略引擎共享同一套策略逻辑代码，避免 "回测时用 A 算法、实盘时用 B 算法" 的不一致问题。WASM 编译的策略天然满足此要求——同一份 wasm 二进制既可用于回测也可用于实盘。

### CHERR-3: 加入 OpenTelemetry 可观测性

建议增加 **OpenTelemetry** 集成，跟踪每个请求的端到端延迟（从 HTTP 请求到 SQL 查询完成）。特别有助于排查 WebSocket 推送延迟瓶颈和回测性能问题。
